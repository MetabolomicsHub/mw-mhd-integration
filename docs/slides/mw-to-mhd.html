01 · The problem

Many repositories, one schema

MetabolomicsHub aggregates datasets from many source repositories. For cross-repository search, indexing and announcement to work at all, every dataset has to arrive in one common, validated schema.

Metabolomics Workbench is one such source. This repository is the adapter between them — and nothing more than that.

It does not define the target model. The schema, the graph builder, the validators and the announcement format all live in mhd-model. This repo supplies only what it means to be Metabolomics Workbench.
02 · The problem

Four things make this genuinely hard

Almost every apparent oddity in the code traces back to one of these.

The JSON isn't valid JSON Responses arrive with concatenated objects, duplicated keys and illegal control characters. They must be repaired before they can be parsed.
Free text must become ontology terms MHD wants {source, accession, name} triples. Workbench gives human-typed strings like “ABI Sciex 4000 Qtrap”.
One study holds many analyses Often heterogeneous — MS and NMR side by side in the same record, needing different treatment.
Required fields are often absent Titles, descriptions and licenses that the target profile requires are simply missing from older source records.
None of this is a criticism of Workbench — it is why an adapter layer has to exist at all, rather than a direct schema translation.
03 · The maplearn this once — it colours every later diagram

Two repositories, one contract

The rule of thumb for the rest of the talk: this repository knows about Metabolomics Workbench; mhd-model knows about MetabolomicsHub. Neither knows the other's internals.
04 · The mapdefined by mhd-model

An MHD file is a graph, not a record

  • NODESTyped entities — study, person, protocol, assay, sample, raw-data-file.
  • EDGESTyped and directional, each carrying a forward and reverse name.
  • VALUESNot strings but CV terms — {source, accession, name} pointing at real ontologies.
That third point is the whole job. Turning Workbench's free text into controlled terms is what the converter actually spends its time doing.

06 · The journeymw2mhd · mw_utils.py

Download, then repair

Cache-first, always

Every fetch checks disk before the network. After one pass the whole pipeline runs offline — which is what makes a 3,700-study batch tractable and re-runnable.

Repair before parse

Four regex passes make the response parseable at all; duplicate keys are then collapsed into lists via a JSON object_pairs_hook instead of silently overwriting each other. 

# mw_utils.py:257 — patch_json_text()
}{            → }, {        join objects
"x":"y":"z"   → "x":"y z"   fix pairs
"x":}         → "x":{}}      fill empties
\x00-\x1F     → stripped   control chars
This reads like a hack until you see the input. It is the reason 3,712 of 3,718 studies parse at all.
07 · The journeymw2mhd · builder.py:280

Select the analyses

  • KEEPAnalyses whose type contains MS.
  • DROPAnything else — logged as a warning, not a failure.
  • FAILOnly when no MS analysis remains.

This is why mixed studies survive: ST000019 (NMR + MS) and ST000098 (3 MS + 3 NMR) both convert, keeping only their MS analyses.

A simplifying assumption worth flagging: study-level metadata is taken from the first analysis after sorting. Where analyses disagree, that one silently wins.
08 · The journeymw2mhd · builder.py:317

Preconditions — the four hard stops

Before building anything, the converter demands a study summary plus three specific fields. Each missing one is a raise ValueError.

  • 1study summary must be fetchable
  • 2license URL must be present
  • 3submission date must be present
  • 4release date must be present
Read these four lines before diagnosing any conversion failure — they account for most of them. 
# ST004083 — all four pass
submission_date : 2025-07-31
release_date    : 2025-08-25
license         : CC BY-NC-ND
license_url     : creativecommons.org/
                  licenses/by-nc-nd/4.0/deed.en
A small detail with visible output: a validator appends a trailing slash to the license URL, which is why the study node's license ends …/deed.en/.
09 · The journeyorder matters — later nodes reference earlier ones

Build the graph, in order

Step 8 is a modelling decision, not a data fact: with no DOI available, the legacy converter asserts “pending publication” for every single study.
The builder object itself — add, link, create_dataset — belongs to mhd-model. What this repo owns is the order, and what maps to what.
10 · The journeymw2mhd · the intellectual core

Free text becomes a controlled term

Two mechanisms. Static maps at the top of builder.py cover known vocabulary. A 671-row crosswalk file covers instruments and ontology terms.

The crosswalk isn't MW-specific — it carries MetaboLights and GNPS columns too. It's a shared translation table.

Nothing is silently dropped. Unmappable values become x-mw-* extension nodes, so the prefix marks exactly where semantic mapping was incomplete. ST004083 has 48 of them.

The header names the schema and profile it claims to satisfy — so validation later is a check against the file's own declaration, not an external guess.

legacy-profile is the only profile implemented. The MS profile branch in the convertor factory raises NotImplementedError.
13 · The journeymw2mhd · a conditional second pass

Enrichment: a safety net, not a stage

Summary fields

Fires if license or dates are missing — or if the release date merely echoes the submission date, a known fallback artifact. Re-fetches and patches.

Raw data files

Fires only if the graph has no raw-file nodes. Scans the file listing, including inside archives, and adds nodes plus edges.

Both paths are conditional. For a well-formed study neither fires — ST004083 needs no enrichment at all. Its 106 raw-file nodes came from the builder, not from here.
Be precise about the corpus. No output on disk contains a GNPS URL, and 153 of 600 sampled outputs have no raw-file nodes. The 3,718-study corpus was generated before this pass was wired in, and does not reflect it. Re-running the batch would change those outputs.
14 · The journeymostly mhd-model

Validate, then announce

validate is a pure re-export of mhd-model's commands. This repository contains no validation logic of its own — the schema and the profile rules both belong to the library.

An announcement is the flattened, public-facing summary derived from the graph. mhd-model generates the base; this repo then walks the graph to recover what the base omits.
